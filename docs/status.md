## Reporting correction — 0.4.5 preparation

The owner requested an implementation fix after the comparison. The publisher now commits a per-accessory report for both tiles before sending any events. Synchronous callback getters return that report with freshness/availability checks. This deliberately restores the old publisher's GET contract: HAP's async onGet path awaits even an immediate returned value, leaving a window for an earlier read to overwrite a newer reported characteristic value. A new actual-HAP regression first reproduces that baseline race for garage and bolt, then checks that a report arriving after read start survives read completion with the new handlers. This is a concrete race being corrected, not proof that it caused the owner's particular stale display.

Both tiles publish current then target, with three explicit reports two seconds apart on a new terminal garage state or bolt state. Each publication uses one HAP reporting method per field, not an ordinary update followed by a duplicate explicit update. Ordinary runtime observations continue reconciliation. Reads and events share the committed values. Preparation now reports the matching Opening/Closing current with its new target; this represents preparation, not sensor proof of travel. A target generation guard rejects delayed SET completions superseded by newer feedback, and cached/new accessories initialize their reports during sync.
